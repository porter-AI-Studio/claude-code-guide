附錄 A · 通訊協定

MCP 協定規格與底層通訊解析

剖析 Model Context Protocol 的訊息傳輸管道、連線信號交換以及 JSON-RPC 2.0 標準規範封包。

一、 MCP 傳輸管道比較

Model Context Protocol (MCP) 是一種用於連結客戶端 (如 Claude Code) 與後端工具服務 (MCP Server) 的公開標準協定。在底層傳輸方面，MCP 主要支援兩種「傳輸管道 (Transport Channels)」：

管道類型 通訊管道底層 連線特點 常見應用情境
Stdio 管道 Standard Input / Standard Output (系統標準 I/O) 極速、免配置網絡、本機行程間通訊 (IPC)，生命週期隨 Host 進程啟閉。 Claude Code 本地運行、執行 Node 或是 Python 等本地腳本。
SSE 管道 HTTP Server-Sent Events + HTTP POST 跨主機聯網通訊。Server 向 Client 單向發送事件流，Client 通過 POST 請求將控制指令發送回 Server。 雲端微服務整合、跨容器遠端資源存取。

對於 Claude Code 而言，最常見且預設的連線模式就是 Stdio。當你使用 `claudecode` 啟動對話時，它會在背景派生 (Spawn) 出一個獨立的 MCP Server 進程，透過標準輸入輸出 (`process.stdin` / `process.stdout`) 以行分隔 (Line-delimited) 的 JSON 格式交換訊息。

二、 JSON-RPC 2.0 通訊標準

無論是 Stdio 還是 SSE 管道，MCP 的控制信令全部遵循 JSON-RPC 2.0 協定格式。每次請求與響應必須具備以下三個核心欄位：

  • jsonrpc：字串，值必須固定為 "2.0"。
  • id：整數或字串，用於唯一識別一次請求。響應封包必須攜帶相同的 id 以進行匹配。如果是單向的通知 (Notification)，則無須提供 id。
  • method / result / error：請求中使用 method 指定方法名稱，響應成功時使用 result 載入回傳值，失敗時使用 error 載入錯誤訊息。

三、 初始化連線流程 (Handshake)

當 Claude Code 啟動 MCP Server 進程後，第一件事是進行**初始化握手 (Initialize Handshake)**。在此步驟中，雙方交換通訊版本與能力宣告 (Capabilities)。

1. 初始化請求 (Client ➔ Server)

客戶端告知其採用的協議版本（例如 2024-11-05）以及其客戶端名稱資訊。 

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2024-11-05",
    "capabilities": {
      "roots": { "listChanged": true }
    },
    "clientInfo": {
      "name": "claude-code",
      "version": "1.0.0"
    }
  }
}

2. 初始化響應 (Server ➔ Client)

服務端確認接受該版本，回報其所擁有的能力（例如支援 Tools、支持 Resources 訂閱功能）。 

{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2024-11-05",
    "capabilities": {
      "tools": { "listChanged": false },
      "resources": { "subscribe": true }
    },
    "serverInfo": {
      "name": "codegraph-server",
      "version": "0.9.0"
    }
  }
}

四、 列出與呼叫工具的封包細節

握手完成後，客戶端會調用 tools/list 取得當前 MCP Server 所有暴露出的工具清單。當 LLM 決定使用工具時，則會送出 tools/call。

1. 列出工具清單 (Client ➔ Server)

{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/list"
}

2. 傳回工具定義 (Server ➔ Client)

服務端會以標準的 JSON Schema 返回所有工具的參數限制。 

{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "tools": [
      {
        "name": "grep_search",
        "description": "在指定目錄下執行全文關鍵字搜尋",
        "inputSchema": {
          "type": "object",
          "properties": {
            "query": { "type": "string" },
            "path": { "type": "string" }
          },
          "required": ["query"]
        }
      }
    ]
  }
}

3. 執行工具呼叫 (Client ➔ Server)

當 Claude 提出工具使用建議並獲得使用者授權後，Client 將發送 tools/call 請求，在 arguments 中攜帶帶入的實參。 

{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "grep_search",
    "arguments": {
      "query": "TODO",
      "path": "./src"
    }
  }
}

4. 返回執行結果 (Server ➔ Client)

服務端執行本地代碼（例如調用 ripgrep 或讀取資料庫），並將結果以字串數組的形式返回給 Client。 

{
  "jsonrpc": "2.0",
  "id": 3,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "找到 2 處匹配：\nsrc/index.js:12: // TODO: fix this\n..."
      }
    ]
  }
}

五、 資源讀取與訂閱封包

除了主動調用工具，MCP 還定義了**資源 (Resources)** 機制，讓 Server 可以向 Client 暴露唯讀的文件或資料庫內容（例如 Log 監控日誌）。

當客戶端想讀取資源時，會送出 resources/read 請求，在參數中攜帶資源的 URI（例如 log://localhost/today）：

ℹ️
通知 (Notification) 的單向通訊

當 MCP Server 內部的資源發生改變時，如果 Client 已經註冊了訂閱能力，Server 可以發送一個不帶 id 欄位的 notifications/resources/updated 通知。這種通知不需要 Client 的回應，屬於單向通訊流。

六、 開發除錯與故障診斷

在開發自訂 MCP Server 時，如果連線遭遇問題，您可以使用以下技巧進行除錯：

  1. 嚴禁混雜標準輸出：在 Stdio 管道下，Server 本身任何的 console.log()、print() 都會被 Client 誤解析為 JSON-RPC 封包。這會造成連線立即中斷。所有 Debug 日誌**必須**輸出至標準錯誤輸出 (Stderr，即 console.error())。
  2. 使用獨立偵錯工具：可以使用官方開發的 @modelcontextprotocol/inspector 工具，它提供了一個網頁 GUI，能讓你單獨向 MCP Server 發送 `initialize` 與 `tools/list` 封包，觀察通訊是否正常。
