附錄 C · 終端環境

終端 Pager 控制與中文字元編碼故障排除

解決 AI 代理在讀取長文件時卡死，以及 Windows 繁體中文環境下控制台顯示亂碼的根本機制與優化方案。

一、 終端 Pager 的運作原理

在 Unix-like (macOS/Linux) 與 Windows 系統的命令行介面中，許多常用指令（例如 git log, git diff, man）在輸出大段文字時，預設不會直接將文字一次性全部印在螢幕上。相反地，它們會將輸出傳送給一個稱為 **Pager (分頁器)** 的系統工具。

最常見的 Pager 工具是 less 或 more。

  • 當 Pager 接收到長文本時，它會接管終端螢幕。
  • 它會在底部顯示一個游標，等待使用者按下 Space (翻頁)、Enter (下移一行) 或 q (退出分頁器並返回 shell)。

二、 為什麼 Pager 會導致 AI 代理卡死？

這種翻頁機制對人類工程師極其友善，但對於 Claude Code 這類非交互式的 AI 代理程序來說卻是一場災難：

  1. 等待使用者輸入阻斷：當 Claude 發送 git log 給子進程 shell 時，作業系統隨之派生出 less 分頁器。
  2. 無法識別 EOF (文件結束符)：less 開始在標準輸出中等待用戶輸入 q。由於 Claude 是以自動化腳本捕捉輸出，它並不知道子進程已經「暫停並卡在分頁器中」，因此會無限期掛起（Hang）等待輸出結束。
  3. Token 消耗與超時：這會導致整個對話流程逾時卡死，甚至消耗額外的 Token。

終極解決方案：PAGER=cat

為了解決這個問題，Claude Code 在啟動子進程時，會主動向環境變數寫入 PAGER=cat。

cat 本質上不是一個分頁器，它只是一個把內容直接列印到標準輸出的工具。透過將 Pager 重新導向為 cat，所有 Git 指令將會一次性吐出所有文字，子進程隨後立即退出，AI 代理便能瞬間讀取全部結果： 

export PAGER=cat
git log -n 5

三、 Windows 中文字元編碼危機 (CP950 vs UTF-8)

在 Windows 環境下（特別是繁體中文語系），終端機的字元編碼常導致 UI 亂碼與腳本崩潰。這是由於以下衝突造成的：

  • Windows 預設代碼頁：繁體中文 Windows 系統的主控台預設代碼頁為 CP950 (Big5 編碼變體)。
  • LLM 與 現代工具輸出：Claude Code 核心、LLM APIs 以及多數 Node.js/Python 現代開發套件，預設皆採用國際標準 UTF-8 編碼輸出。

當 UTF-8 的位元流強行被 CP950 解碼時，螢幕上就會出現大量中文亂碼（例如大頭照匯入時產生特殊亂符，或是控制台錯誤訊息顯示亂碼）。

四、 如何完美配置 Windows/Mac 終端編碼

1. Windows PowerShell 設定 UTF-8 環境

若要避免在 PowerShell 中執行任何腳本出現亂碼，請在執行指令前強制切換代碼頁至 65001 (即 Windows 中的 UTF-8 代碼頁)，並調整輸出流編碼： 

chcp 65001
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8

2. Python 腳本編碼修正 (Antigravity 強制規範)

若您在開發自動化工具或編寫與 Claude Code 互動的 Python 腳本時，必須在腳本進入點加入以下編碼修正，以確保在 Windows 上也能順利輸出包含 Emoji 或中文字元的 UTF-8 日誌： 

import sys
import io

if sys.platform == 'win32':
    sys.stdout = io.TextIOWrapper(sys.stdout.buffer, encoding='utf-8', errors='replace')
    sys.stderr = io.TextIOWrapper(sys.stderr.buffer, encoding='utf-8', errors='replace')
💡
VS Code 終端設定

強烈建議在 VS Code 的 settings.json 中設定預設終端字型為支援 Unicode 且支援等寬顯示的字型（如 Fira Code 或 Noto Sans TC），這能有效防止終端圖示 (Icons) 與中文對齊跑版。
