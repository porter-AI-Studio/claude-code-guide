附錄 F · Pro 額度

Pro 方案額度機制詳解

Claude Code Pro 版每週額度並不是固定「訊息數量」，而是依照運算量（Token 消耗）來限制。 一般用戶的經驗是：在 Pro 方案下，若每天持續進行程式開發或除錯， 通常 3–4 天就會用完一週額度，需要等到週期重置才能繼續使用。

一、額度機制

短期限制：5 小時滾動視窗

每 5 小時有一個使用上限，達到後需等待舊請求移出視窗才能恢復。 Pro 用戶在此視窗內可處理「數十則一般訊息」，但若是程式碼任務，消耗速度會更快。

長期限制：每週總額度

Pro 方案有一個「週限額」，用戶若持續高強度使用 Claude Code，通常在 3–4 天就會觸頂。 一旦觸發週限額，必須等到週期重置才能恢復。

二、Token 消耗來源

  • 輸入長度：長篇程式碼或需求說明會消耗更多 Token。
  • 上下文累積：對話越長，每次回覆需要讀取更多歷史內容。
  • 附件：上傳 PDF、程式碼壓縮檔等會顯著增加消耗。
  • 模型能力：使用 Opus 進行深度推理比 Sonnet 消耗更快。

三、Pro 與 Max 的差異

方案 短期額度（5 小時） 每週額度 適合族群
Pro 數十則一般訊息，程式碼任務消耗快 約 3–4 天高強度使用即觸頂 日常中度使用者
Max Pro 的數倍 足以支撐全職開發者長時間使用 重度開發、研究工作者

四、常見誤解：切換模型能省 Token？

在同一個對話裡頻繁切換模型（例如 Sonnet ↔ Opus），並不會真正省下 Token。 原因是：每次模型回覆都必須重新讀取整個對話上下文，而上下文長度才是消耗的主要來源。

  • 上下文共享：不管是 Sonnet 還是 Opus，模型都要讀取同一段對話記錄。
  • 消耗來源：主要來自「輸入長度 + 輸出長度」，而不是模型切換次數。
  • 模型差異：不同模型的推理能力不同，但 Token 計算方式相同，切換本身不會減少消耗。
🔑
省 Token 的關鍵不是模型切換，而是控制上下文長度與輸入精簡度。

五、使用建議

  • 避免在同一對話中無限追加需求：上下文越長，消耗越快。建議完成一個階段後開新對話。
  • 將大型任務拆分：一次只處理一個模組或功能，避免單次請求過大。
  • 精簡輸入：提供必要的程式碼片段即可，不需貼上整個專案；用簡短描述代替冗長背景說明。
  • 善用 Sonnet：日常程式碼任務用 Sonnet，遇到複雜推理再切換 Opus，可有效節省額度。
  • 注意週限額：若需要長時間高強度使用，建議升級 Max，否則容易在工作進行中途強制停擺。
⚠️
全職開發者注意：若你每天長時間仰賴 Claude Code 進行開發工作， Pro 方案的週限額可能不夠用。建議評估升級至 Max 方案，以避免頻繁觸頂影響工作效率。
